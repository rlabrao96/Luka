- **Shared-card charge classification (2026-07-13)** — branch `feat/shared-card-classification` (not yet merged), migration 056. Solves a gap partner-card attribution didn't cover: a card *physically* shared between two household members (e.g. one Visa both partners carry) has no signal at ingestion for whose charge is whose — unlike a `joint` account (auto-`shared`) or a Plaid authorized-user `partner` card (owner decides via hand-off). Flagging a bank account `account_type='shared_card'` pends every new non-transfer charge (`transactions.needs_classification=True`), invisible to every money aggregate (dashboard/budgets/settlement/per-account balance — same totals-exclusion predicate as orphans/transfers/refund pairs) until sorted. Both partners see the identical **"Por clasificar"** queue (`GET /transactions/por-clasificar?household_id=`) and either can sort a charge **four ways** via `POST /transactions/{id}/classify` (`owner_personal` / `partner_personal` / `owner_shared` / `partner_shared`) — first-to-sort wins, a second call 409s `already_classified`. Personal outcomes never touch the household balance; shared outcomes credit the **effective payer** — `partner_shared` means the partner fronted the money on the owner's card, so settlement owes the partner back, not the card's nominal owner (mirrors the existing `effective_owner_id` pattern from partner-card attribution, via a new `effective_payer_id` helper reused by settlement/contribution/breakdown/member-stats). A daily cron notifies every active member once/day while charges sit unsorted (idempotent per user/day). Switching an account's type TO `shared_card` pends its existing history; switching AWAY clears the pending flag and runs the normal split backfill. **Leave-household edge:** a departing member's pending shared-card charges resolve to the remaining owner's personal expenses (`resolve_pending_to_owner_on_leave`) so the queue — a two-person surface — never holds rows against a non-member; this runs alongside the existing `revert_attributions_for_member` call in `remove_member`. Frontend: `PorClasificar.tsx` renders the queue with a four-way sort control, wired into the dashboard and `useTransactions.ts`. 39 dedicated tests (`test_shared_card_classification.py`) + full attribution/household/settlement/budget/dashboard/contribution/equity/joint/totals regression green; `tsc --noEmit` clean. **Deferred follow-ups:** (1) re-open/re-sort a mistakenly-sorted charge — v1 has no "undo" once a charge is classified (short of admin SQL); (2) a real partner-picker UI for `ambiguous_recipient` in >2-member households — the backend already accepts an explicit `partner_id` to disambiguate, but no frontend picker exists yet (mirrors the same gap in partner-card attribution); (3) *(minor, from final review)* `get_pending_transactions`' pre-existing `needs_classification` category-bucket key collides in name with the new split-classification column — an unsorted shared-card charge with no category can appear in both the category-review list and the Por-clasificar queue (cosmetic UX overlap, no money impact); (4) *(minor, from final review)* `classify` reads-then-writes `needs_classification` without `SELECT … FOR UPDATE`, so two truly-simultaneous sorts could both pass the first-wins guard (benign last-writer-wins, not corruption) — add a row lock if hardening. **Final-review blocker fixed pre-merge:** `get_dashboard_summary` hand-rolled its exclusion list and never got the `needs_classification` exclusion, leaking pending charges into the owner's dashboard total/category chart; fixed + regression-tested.

- **Migration constraint naming inconsistency** (Plan 1 Task 1 review): `ck_subscription_overrides_split_type` (plural) vs the existing `ck_subscription_override_status` / `_day` (singular) on the same table. Cosmetic; consider a follow-up migration that renames the older two for consistency, or accept the new plural form as canonical.
- **Race condition in `reclassify_subscription_split` cascade** (Plan 1 Task 4 review): the per-tx UPDATE-then-INSERT loop can create duplicate `transaction_splits` rows if two requests race for a tx that has no existing split row. Schema doesn't enforce uniqueness on `transaction_splits.transaction_id`. Recommended fix: add a UNIQUE constraint migration on `transaction_splits.transaction_id` and convert the loop to `INSERT ... ON CONFLICT (transaction_id) DO UPDATE`. Also benefits 4 other insertion sites in the codebase.
- **Test fixture model registration gap** (Plan 1 Task 4 review): `noqa: F401` model imports are sprinkled across `test_subscription_reclassify.py`, `test_user_budget_settings.py`, `main.py`, `alembic/env.py`, and `tests/conftest.py` to register FK targets in SQLAlchemy metadata. The right fix is a central `backend/modules/__init__.py` (or similar) that imports all models once.
- **Test spacing in cascade tests** (Plan 1 Task 4 review): `test_subscription_reclassify.py::test_cascade_updates_last_3_months_only` uses `timedelta(days=31 * months_ago)` instead of `dateutil.relativedelta(months=N)`. Works correctly with an inline comment, but `relativedelta` would be more idiomatic.
- **Helper duplication across test files** (Plan 1 Task 5 review): `_get_seed_user`, `_get_seed_household_id`, `_user_by_email` are now defined in 4+ test files with slight naming variations. A shared `backend/tests/helpers/seed.py` would consolidate them.
- **`get_budget_v2` size growth** (Plan 2 Task 9 review): grew significantly with the inline personal-view bucketing logic and, after the 2026-04-21 drilldown work, `v2_service.py` is now ~1.7k lines; could be extracted to a private helper or split into `v2_service.py` + `v2_sankey.py` + `v2_queries.py` + `v2_drilldown.py`.
- **`update_personal_allocation` and `update_savings_target` parallel implementations** (Plan 2 Task 11 review): could share a single `update_user_budget_settings_field` helper.
- **Hogar Sankey allocation-node `if` blocks repetition** (Plan 2 Task 7 review): the 5 `if X > _ZERO: nodes.append(SankeyNode(...))` stanzas could be DRY'd via a list-of-tuples loop. Cosmetic.
- **Missing `otras_fuentes` synthetic-source unit test** (Plan 2 Task 7 review): `test_budget_v3_sankey.py` doesn't directly test the overspent-month `otras_fuentes` emission path. The logic is correct by inspection and integration-tested via the flow conservation matrix, but a focused unit test would harden coverage.

## Known Issues

- **No browser-based UAT for authenticated flows** — Google OAuth's automation-detection blocks chrome-devtools-mcp + browser-use from signing into Luka. Auth changes are verified via TypeScript build + backend curl tests (401 paths, HS256 alg-confusion rejection) + user's own manual smoke. Pre-release tagging should still include a manual click-through by the maintainer.
- **WhatsApp Business API approval** — Currently using test/dev mode. For multi-user production use, Meta's official WhatsApp Business API approval process is needed.
- **No frontend test infrastructure** — No Jest, Vitest, or Playwright configured. Backend has 56 test files (~401 tests) but frontend has zero tests.
- **No CI/CD pipeline** — No GitHub Actions workflows. Backend tests are run manually (`pytest`). Deployment is manual via Railway/Vercel.
- **Pre-existing `test_sankey_flow_conservation_fixed_outflow_exceeds_income` failure** (`backend/tests/test_budget_v2_endpoint.py`) — inserts a transaction with `status='categorized'`, but migration 039 tightened `ck_transactions_status` to `('pending','settled','orphan')`. Fails in isolation; unrelated to any of the 2026-04-21 budget work. Fix by updating the seed to a valid status (or loosening the check constraint if 'categorized' is needed).
